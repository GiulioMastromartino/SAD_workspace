SAD_Project — Finalized Plan

6U CubeSat Hamiltonian quaternions Star tracker + full Basilisk sensor suite 8 variable-thrust jets + full Basilisk actuator suite Detumble → Slew → Track Modular C++ / Simulink-first

Status: FINALIZED PLAN. Supersedes SAD_Project_PROPOSAL.html. No code written yet — this document defines the final architecture, the complete reuse inventory of Basilisk sensors/actuators, the modular C++ module decomposition, and the path to a first-class C++ library embeddable in Simulink (and still callable from Python).

0. Objective (clarified)

Build a modular C++ library of spacecraft attitude-dynamics components — not one monolithic module. Each component is a self-contained C++ module with a flat C interface and a Simulink S-function wrapper, so it can be dropped into a Simulink model as a first-class block, while remaining callable from Python for parity testing and Monte-Carlo campaigns. Python becomes a thin orchestration/test layer over the C++ modules; Basilisk remains the reference truth model.

  • First-class C++ module: each module compiles to a shared library + MEX S-function, exposes typed input/output/state structs, init/reset/step API, and is registered in Simulink's Library Browser.
  • Modular: one module per concern (dynamics, each sensor, each actuator, environment, estimator, controller, allocator, mission sequencer). Modules compose through typed message ports, mirroring Basilisk's message-passing architecture.
  • Reuse: every Basilisk sensor and actuator that is physically relevant to a 6U CubeSat is reused (wrapped or mirrored), not reimplemented, so the C++ modules stay bit-consistent with Basilisk reference runs.

2. Modular C++ architecture

Each box below is one independently compilable module. Arrows are typed message ports (Basilisk-style). A module never links against another module's internals — only against the shared sad_core math/message library.

SAD_Project/
├── cpp/
│   ├── core/            # sad_core: math, quaternions, DCM, messages, RNG, integrator
│   ├── dynamics/        # sad_dynamics: rigid body EOM + orbital env coupling

│   ├── sensors/         # one module per sensor (see §3.1)
│   ├── environment/     # sun, mag field, atmosphere, eclipse, albedo, planet ephemeris

2.1 Module interface contract (applies to every module)

// Every module implements this minimal C ABI (extern "C") so Simulink can call it.
typedef struct { double x[...]; int n; } sad_input_t;   // typed per module
typedef struct { double y[...]; int n; } sad_output_t;
typedef struct { double z[...]; int n; } sad_state_t;

void   mod_init(sad_state_t* s, const sad_params_t* p);   // Reset/initialize
void   mod_step(const sad_input_t* u, sad_state_t* s, sad_output_t* y, double dt);
void   mod_reset(sad_state_t* s);                        // zero state
size_t mod_state_size(void);

Simulink side: each module ships a Level-2 C MEX S-function (sad_<mod>_sfun.c) exposing the same ports, plus a .tlc for Simulink Coder. Python side: a pybind11 shim exposes init/step/reset for parity tests.

2.2 Data flow (one control tick)

  1. sad_dynamics propagates quaternion state (Heyoka or RK4) using commanded wrench.
  2. Sensors (sad_startracker, sad_imu, …) read true state + environment → noisy measurements.
  3. Estimation modules fuse measurements → estimated attitude/rate.
  4. Controller modules compute desired torque from estimated state + reference.
  5. Allocation modules map desired torque → thruster on-times / RW torques / MTQ dipoles.
  6. Actuator modules apply commands → actual wrench fed back to dynamics next tick.
  7. sad_mission_sequencer selects mode (detumble/slew/track) and reference.

4. Core dynamics (SAD-specific)

4.1 State vector

y = [r(3), v(3), q(4), omega(3)] = 13 states. Quaternion scalar-last (Hamiltonian), renormalized every RHS evaluation.

q_vec_dot = 0.5 * (q4 * omega + cross(omega, q_vec))
q4_dot    = -0.5 * dot(omega, q_vec)

4.2 Quaternion PD controller

q_err = q_desired * q_current^{-1}   (Hamiltonian product)
tau   = -K * q_err_vec - P * omega     (detumble: q_desired = identity)
  • Detumble: q_desired = [0,0,0,1], high K (rate damping)
  • Slew: q_desired = ACS_SLEW_QUAT (90° about +Z), moderate K
  • Sun-track: q_desired = sun_pointing_quaternion(), cone check (15° half-angle)

4.3 Star tracker model

Returns noisy q_BN or dropout (None) on motion blur / Sun flare / rate cap. Mirrors Basilisk starTracker.

4.4 Sun-pointing orientation constraint

After slew, keep body +X within 15° of Sun. sun_pointing_quaternion() builds DCM like cubesat_12u_sim's sun_pointing_sigma(), final conversion to quaternion.

4.5 Optional RW path

tau_body = -K * q_err_vec - P * omega
tau_rw   = RW.step(tau_body, dt)       # first-order + saturation
u        = allocation_pinv(F=0, tau=tau_rw)

6. Resolved open questions

  1. LEO drag/J2 — off by default for the ~180–600 s attitude mission (matches 12U baseline); enabled via config flag for LEO-realism runs. Decision: off by default, configurable.
  2. Star tracker model — reuse Basilisk starTracker as the reference sensor; Python mirror implements the same error/dropout model. Decision: Basilisk ST (not a separate Kalman/Live split).
  3. Slew target — 90° about body +Z confirmed (matches ACS_SLEW_QUAT). Decision: confirmed.
  4. Modularity — one module per concern (not one monolithic C++ module); see §2 and §3. Decision: modular.
  5. Simulink embedding — each module ships a Level-2 C MEX S-function + .tlc; C ABI in §2.1. Decision: first-class Simulink blocks.

7. Build & integration plan

  1. Core library sad_core: quaternion math, DCM, message structs, RNG, integrator. Header-only + compiled utils.
  2. Per-module targets: each module is a CMake target producing libsad_<mod>.so/.dylib + sad_<mod>_sfun.mex* + pybind shim.
  3. Parity tests: Python tests drive both the C++ module and the Basilisk reference; assert state trajectories agree within tolerance.
  4. Simulink: assemble a reference model using the S-function blocks; generate code via Simulink Coder for HIL/flight-software builds.
  5. Monte Carlo: Python driver dispatches C++ modules (via pybind) over the dispersed set; reuses tuning/profiling.py.

8. Execution roadmap (phased)

  1. Phase 0 — Scaffold: CMake skeleton, sad_core, module interface contract, pybind + MEX shims, CI.
  2. Phase 1 — Dynamics + environment: sad_dynamics, gravity, drag, SRP, sun/mag/atmosphere/eclipse modules.
  3. Phase 2 — Actuators: thruster, RW, MTQ, VSCMG, fuel tank, saturation (all reused from Basilisk).
  4. Phase 3 — Sensors: star tracker, IMU, magnetometer, CSS, camera, temp, nav (all reused).
  5. Phase 4 — Estimation: nav aggregate, sensor comms, EKF/UKF/SuKF family.
  6. Phase 5 — Control + allocation: quaternion PD, MRP family, pointing, thruster/RW/MTQ allocation, firing logic.
  7. Phase 6 — Guidance + mission: pointing refs, Lambert/DV, mission sequencer (detumble→slew→track).
  8. Phase 7 — Simulink integration: S-functions, Library Browser, reference model, codegen.
  9. Phase 8 — Verification: parity tests, Monte Carlo, KPI report.

10. Testing strategy

  • Unit parity: each C++ module vs Basilisk reference over randomized inputs; tolerance 1e-9 (state), 1e-6 (sensors).
  • Integration: full mission run C++ vs Python/Basilisk end-to-end; compare trajectories.
  • Simulink: model runs in normal mode and codegen (ERT) mode; compare against C++ reference.
  • Monte Carlo: 500-run dispersed campaign; report KPI distributions.
